### Final desktop Agent Chat behavior

- The Agent Chats implementation converged on routines waking their owning persistent thread rather
  than creating background child threads. A routine consequently inherits the Agent Chat's current
  model, reasoning and provider options, runtime access and interaction modes, standing
  instructions, transcript, provider session, worktree, and checkpoint pipeline. Compatibility
  decoding for the discarded child-thread representation remains only so existing history opens
  safely; the obsolete execution path was removed before `ecd1ebe96`.
- Routine trigger messages remain durable and linked to the run for idempotent recovery, but desktop
  and mobile remove them only at feed presentation time. Agent responses, tool calls, approvals,
  diffs, and history/cursor synchronization remain unchanged.

### Follow-up engineering conclusions

- Upstream T3 already contains an iOS Agent Awareness system with APNs registration, notification
  preferences for approval/input/completion/failure, notification deep links, and an aggregate Lock
  Screen/Dynamic Island Live Activity. Samuel's first TestFlight build explicitly disables that
  capability. Enabling it requires fork-owned APNs/signing and a push relay; a direct Tailscale
  connection cannot wake a suspended iPhone by itself. Existing notifications navigate into a
  thread but do not yet expose Steer, Approve, Stop, or reply actions.
- Self-managed Agent Chat routines should use the existing thread-scoped `t3-code` MCP server shared
  by Codex, Claude, Cursor, Grok, and OpenCode. Model-facing list/create/update/enable/delete/run-now
  tools should derive the environment and thread from the MCP credential, permit an Agent Chat to
  manage only its own routines, and dispatch the existing event-sourced routine commands rather
  than write storage directly. Routine capability issuance must be separated from the current
  Agent Browser Access gate. This is a design conclusion only; no routine-management MCP tools were
  implemented in this session.
- The observed claim that iOS mid-run prompts queue instead of steering now conflicts with the
  current mobile outbox contract and focused test, which intentionally deliver connected
  existing-thread messages while the thread is busy so they can steer. Treat the physical behavior
  as an unresolved acceptance discrepancy requiring provider/device reproduction before changing
  orchestration.

## 23:07 — Local Slack bridge for one durable T3 thread

- **Outcome:** Added the fork-specific `@tradewiz/slack-thread-bridge` app. A private Slack Socket
  Mode DM now has an implementation path into `thread.turn.start` on one configured existing T3
  thread, and the bridge subscribes to the same thread to return its final assistant response.
  Scheduled Agent Chat completions, failures, and attention requests are proactively forwarded to
  Samuel's DM without a second model conversation or hosted webhook.
- **Decisions:** The integration is a local sidecar over T3's typed authenticated RPC client, not a
  provider adapter or MCP ingress. It requests only `orchestration:read` and
  `orchestration:operate`, accepts only one configured Slack member's text DMs, uses stable Slack
  event IDs for T3 command idempotency, tracks the ordered turn queue for response correlation, and
  leaves approvals and structured user-input handling in T3. A reversible LaunchAgent installer
  keeps the bridge running while the Mac is available.
- **Verification:** Focused app typecheck passed. Six test files passed with 14 tests covering
  pairing-scope exchange, WebSocket ticket secrecy, Slack filtering, response chunking, stable T3
  commands, duplicate delivery, queued-turn correlation, streamed final-message assembly, and full
  routine-response forwarding. The package was formatted with the repository formatter.
- **Recovery:** An initial parallel typecheck/test launch caused both pnpm processes to refresh the
  newly changed workspace and one collided with the Effect TypeScript patch backup. The other
  install completed cleanly; sequential typecheck and tests then passed. No live T3 state was used.
- **Hosted actions:** None. No Slack app, T3 credential, live thread turn, message, LaunchAgent,
  commit, push, or release was created. Live setup still requires the Slack tokens/member ID, the
  chosen Agent Chat thread ID, a one-time T3 pairing exchange, a foreground DM smoke test, and then
  explicit LaunchAgent installation.
- **Repository state:** Implementation, client-runtime export, lockfile, docs, and tests remain
  uncommitted and unpushed alongside pre-existing maintainer changes.
